## 宿題

- 取り組んだレベル：基礎
- 変えた設定やデータ：
  - `CONFIG` の `lora_r` を `16`（元の設定）から `32` に変更した（その他の設定 `lr: 2e-4`, `num_train_epochs: 20`, `lora_alpha: 32` 等は固定）。
- 結果（比較表や数字）：

| 指標・項目 | 元の設定 (`lora_r: 16`) | 変更後 (`lora_r: 32`) |
| :--- | :--- | :--- |
| trainable params (%) | 6,389,760 (0.8421%) | 12,779,520 (1.6701%) |
| 最終 Training Loss (Step 40) | 0.013826 | 0.014902 |
| 学習時間 | 253 秒 | 231 秒 |
| 学習前 `format_rate` / `content_rate` | 0.095 / 0.000 | 0.095 / 0.000 |
| 学習後 `format_rate` | 1.000 (21/21) | 1.000 (21/21) |
| 学習後 `content_rate` | 0.905 (19/21) | 0.952 (20/21) |
| 学習後に残った失敗（内容×） | 2問（No.15, No.20） | 1問（No.20） |

  - **精度の変化**: `format_rate` はどちらも 1.0（全問クリア）だった。`content_rate` は `lora_r: 32` に増やしたことで 0.905 から 0.952 へと向上した。具体的には、元の設定では「成績はいつ出ますか（No.15）」に対して課題の提出期限を当てはめて `needs_review: false` と誤断定していたが、`lora_r: 32` では `needs_review: true`（記載なし・要確認）と正しく回答できた。アダプタの次元数を増やした効果（および `lora_alpha / lora_r` の比率が変わり過学習が抑えられた効果やGPU学習の揺らぎ）により一定の改善が見られた。一方で、「オフィスアワーは事前予約が必要ですか（No.20）」については、`lora_r: 32` でも引き続きオフィスアワーの時間を返して `false` と誤断定した。
  - **学習時間の変化**: 学習対象パラメータ数は2倍（0.84%→1.67%）に増えたが、学習時間は 253秒 → 231秒 とむしろ短縮した。モデル全体（約7.6億パラメータ）に対する追加パラメータの割合が依然として小さく計算負荷がほぼ変わらなかったため、Colab環境の実行タイミングの揺らぎの範囲に収まったと考えられる。

- ファインチューニングが向く場面・向かない場面についての考察：
  - **向く場面**: 学習前にはプロンプトで指示しても `format_rate` が 0.095 とほとんど守れなかった JSON 形式（必須キー `answer`, `needs_review` と型の遵守）や定型文のスタイルが、数分間の LoRA 学習によって 1.0（100%）に改善した。このように、**出力フォーマットの固定や応答トーン・定型文面の統一**にはファインチューニングが非常に有効である。
  - **向かない場面**: `lora_r` を 32 に増やして表現力を高めても、「オフィスアワーの事前予約（No.20）」やセクション6の質問のように、**FAQ内の既知のキーワードを含みつつ書かれていない事実を問う質問に対して、根拠の有無を正確に判断すること（ハルシネーションの完全な防止）までは保証されなかった**。正確な知識の参照や根拠の有無を厳密に判定させる用途にはファインチューニング単体では不向きであり、検索（RAG）やルールベースの検証ロジックと組み合わせる必要がある。
