- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - `uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行したところ、第2回・PDF p.52, p.51, p.60, p.47, p.61 の5ページが返った。
  - 1位の p.52 に「元の重み W は固定して学習しない」「小さな行列 A・B だけを学習（LoRA）」「元の重みを 4bit に圧縮（QLoRA）」という直接の根拠があり、2位の p.51 にも PEFT 全体の中での LoRA・QLoRA の比較が書かれていた。3〜5位は演習手順や FT と RAG の比較など関連話題のページだった。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - 全文投入：ツール呼び出しなし（モデル応答 1回）。
  - ベクトル検索：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し（モデル応答 2回）。
  - Tree：`browse_tree` を4回呼び出し（モデル応答 5回）。ルート → `lec02-main`（基盤モデルの仕組み）→ `lec02-main-s045`（選んだモデルを、いつ・どう直すか）→ `lec02-main-p052`（LoRA と QLoRA）の順に目次をたどり、末端ページの本文717文字を取得した。
  - Graph：`search_graph({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し（モデル応答 2回）。`lec02-main-p052` 等を入口（seeds）として関連ページを取得した。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - 今回の質問は第2回・PDF p.52 の1ページに主な根拠がまとまっていたため、4方式すべてで必要な根拠を取得し正答できた。
  - 一方で、全文投入では入力量が多い影響か「宿題のヒントになりますので〜」という質問意図に沿わない前置きが混じった。また、Tree は p.52 のみをピンポイントで開いたため p.51 の補足は引用されなかった。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **採用したい方式**：ベクトル検索（基本RAG）。
  - **理由**：4方式の中で最も入力トークン数（3,027 tokens）と推定費用（$0.001408）が少なく、応答時間（2.56秒）も短いまま、必要な根拠（p.51, p.52）を正確に取得して回答できたため。
  - **比較条件の限界**：全文投入は全9資料を対象としているのに対し、他の3方式は第1〜3回の本講義資料のみが対象であり条件が完全にはそろっていない。また、今回の1問（単一ページで完結する質問）・各1回のみの結果であり、複数ページを横断する質問では Graph や Tree の方が有利になる可能性がある。
- 気づき・疑問：
  - 全文投入はモデル応答が1回で済むため応答時間（1.97秒）は最も速かったが、入力トークン数が 117,025 tokens と桁違いに多く、コストも最大（$0.004884）になった。
  - Tree は人間が目次を引くように的確に p.52 へ到達できたが、ツール呼び出しが4回（応答5回）発生するため時間が最もかかり（5.55秒）、入力トークンもベクトル検索の約3倍に増えた。
  - Graph はベクトル検索より関連候補を広げる分トークン数が増えた（3,027 → 5,771 tokens）が、単一ページで完結する質問ではベクトル検索と回答の差が出なかった。質問のタイプに応じて方式を使い分ける重要性を実感した。

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/config.py` の `RAG_TOP_K`（初期値 `5`）を `10` および `1` に変更し、変更前後でツールの呼ばれ方・回答・根拠・トークン数・費用の違いを比較した。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
  - 回答モデル：`gemini-3.5-flash-lite`
  - 対象資料：第1〜3回の本講義資料（`lec01-main`, `lec02-main`, `lec03-main` / `data/rag_data/index.sqlite3`）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - **変更前（`RAG_TOP_K = 5`）**
    - 回答・根拠：LoRA（元の重みを固定し、差分である行列A・Bを学習）とQLoRA（元の重みを4bitに圧縮）を正しく回答。引用は第2回・PDF p.51, p.52。
    - `--trace`：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し（モデル応答 2回）。
    - 時間・トークン・費用：2.56秒 ／ 入力 3,027 tokens・出力 200 tokens ／ $0.001408 USD
  - **変更後①（`RAG_TOP_K = 10`）**
    - 回答・根拠：回答内容・引用ページ（第2回・PDF p.51, p.52）ともに変更前とほぼ同じ。
    - `--trace`：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し（モデル応答 2回）。
    - 時間・トークン・費用：2.61秒 ／ 入力 5,187 tokens・出力 189 tokens ／ $0.002029 USD
  - **変更後②（`RAG_TOP_K = 1`）**
    - 回答・根拠：引用は第2回・PDF p.52のみになったが、LoRA・QLoRAともに必要な内容を正しく回答できた（冒頭に「QLOOR」の誤字あり）。
    - `--trace`：`search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` を1回呼び出し（モデル応答 2回）。
    - 時間・トークン・費用：2.22秒 ／ 入力 1,191 tokens・出力 188 tokens ／ $0.000827 USD
- 改善した例と、残る失敗・制約：
  - **改善した例**：`RAG_TOP_K = 1` に減らすことで、回答の正しさを維持したまま入力トークン数を約6割削減（3,027 → 1,191 tokens）、推定費用を約4割削減（$0.001408 → $0.000827）、応答時間も短縮（2.56秒 → 2.22秒）できた。
  - **残る失敗・制約**：今回は1ページ（第2回・PDF p.52）に根拠がまとまっている質問だったため `RAG_TOP_K = 1` でも正答できたが、複数ページにまたがる質問や検索順位が下がる質問では必要な根拠を取りこぼすリスクがある。また、`RAG_TOP_K = 1` の回答冒頭に「QLOOR」という軽微な誤字が見られた。
- 気づき・疑問：
  - 検索件数を増やす（5→10）と、必要な根拠がすでに上位5件に含まれている場合は回答精度が変わらないまま入力トークン数（約1.7倍）とコスト（約1.4倍）だけが増加することが分かった。
  - RAGでは検索件数を闇雲に増やすのではなく、質問の性質に応じて「取りこぼしを防ぐ件数」と「コスト・入力トークン数」のバランスを実測しながら設計することが重要だと実感した。
